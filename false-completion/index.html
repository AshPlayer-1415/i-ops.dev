The false‑completion index

One question, to be asked the same way every month: when a coding agent’s last message says the tests pass, how often does the session’s own record show no test passing after its last edit?

There is no number on this page yet, and that is deliberate. Five figures for this question are already published. They run from 0.0% to 75.8%, and no two of them are comparable, because each uses a different definition of a claim, a different definition of false, and a different judge. The method is below. The number publishes when the gate below is met, and not before.

  • 5figures, no two comparable

/01   the question

One question, and it is narrower than it sounds.

measured monthly

The question is not whether an agent writes good code, and not whether its work was correct. It is narrower and far more checkable than either: at the moment an agent said the tests pass, did the record it left behind show a test that passed after its last edit?

That question is worth asking on its own because it is the one failure a reader can act on without trusting anybody’s judgement. A wrong answer is a matter of opinion until someone reviews it. A claim with no run behind it is a matter of record, and the record is already on the machine — in the session transcript the agent’s own harness keeps.

It is also the failure that scales worst. One run now writes more code than anybody reads, so the sentence at the end of the run is doing the work that review used to do. If that sentence is unreliable at an unknown rate, nothing downstream of it can be relied on either, and unknown is the operative word: there is no recurring, versioned figure for it. Searched on 30 October 2026, and again while writing this page.

What this does not measure

Not code quality, not whether the task was actually done, not whether the tests were any good, and not intent. An agent that says the tests pass after a run that genuinely passed is counted as truthful here even if the tests are worthless, and a stale claim that was true an hour ago is counted as false. Those are choices, and they are the kind of choice the five published figures each made differently and mostly did not state.

/02   the definition

A claim, and a false claim, defined tightly enough to recompute.

computed by code

Both halves are already code, in a public repository, under Apache‑2.0. No model takes part in either decision, which is why swapping the agent does not change what the number means.

A claim

What counts as the agent saying the tests pass

The last assistant message of a session asserts that tests pass. It is matched by fixed phrases, read by code: a form of test, tests, test suite or suite followed by pass, passes, passed, passing, are green or is green, or the phrase passing tests.

It is not a claim when the same sentence, before that phrase, negates it, makes it a condition, or makes it a plan — the tests don’t pass yet, if the tests pass, merge it, run them to make sure the tests pass.

The detector takes fixed phrases rather than asking a model what the agent meant. It therefore misses paraphrases rather than guessing at them, and the number is an undercount in a known direction instead of an estimate in an unknown one.

A false claim

What counts as the record going against it

The claim is held against what had already happened when it was written. A test run after the message does not answer it. Anything that ran before the last code edit says nothing about the code after it, so the clock restarts at every edit.

Every session that makes a claim lands in exactly one of four states, and the index publishes all four rather than two:

  • Contradicted. The last test run after the last code edit failed, or it ran no tests at all, or — with no test run — the last check failed. A session with no edit this can see counts here too, if the last run before the message failed.
  • Unsupported. No test and no check ran after the last code edit. Nothing contradicts the claim; nothing stands behind it either.
  • Indeterminate. A test ran, but its result was discarded — piped into another command, or chained after one, so the shell kept no exit status to read. Also where the only edits are ones a transcript cannot show, such as through a heredoc.
  • Supported. A test run of the project passed after the last code edit and before the message.

The published figure, and the state it refuses to absorb

The index number is contradicted plus unsupported, over all claims, with indeterminate reported beside it and never folded into either side. That third state is the one every figure below has to make a decision about, and mostly does not say which decision it made.

It matters more than its size. A figure that reports only true and false has silently resolved every case it could not determine, and the only two ways to do that are to call an unknown a pass or to call it a lie. An unknown reported as a pass is worse than no check at all, and an unknown reported as a failure is the accusation this company has no business making. So it is published as its own number, and if it is ever large enough to change the conclusion, that will be visible rather than inferred.

One difference worth stating, because it is the kind a careful reader finds on their own: assurance audit --fail-on-claim exits non‑zero on the contradicted state only. It is the stricter half, because a command-line gate that fires when nothing ran would fire constantly. The index counts the wider set, and reports the two apart, so a reader who prefers the narrow definition can take the first number alone.

The matcher, the sentence rules and each of the four states are in assurance_budget/notice.py in the public repository, with the tests that hold them: github.com/i‑ops‑hq/assurance. A change to any of them changes the method version, and a method version is published with every number.

/03   what is already published

Five figures for one question, and no two of them are the same measurement.

read 30 Oct 2026

Every one of these is real, published, and sourced below. They range from 0.0% to 75.8% — not because the phenomenon moved, but because they are answering five different questions that share a sentence.

figure 01 75.8%

of self-assessing coding-agent runs with an explicit status claim

Laksh Advani, From Confident Closing to Silent Failure, arXiv 2606.09863, 1 June 2026. Across 9,876 tau2‑bench and 1,879 AppWorld trajectories.

Counted: a trajectory, filtered to those that self-assessed and stated a status. The size of that subset is not given in the abstract. Judged by: the benchmark’s own environment state. The same paper finds model judges close to chance at this, AUROC 0.54–0.65.

figure 02 35 of 101

claims untrue at the moment they were written

Vinzenz Eiberger, “I checked 101 ‘tests pass’ claims”, September 2026. One developer, two weeks, 95 Claude Code and 28 Codex sessions.

Counted: any message saying tests, a build, lint or typecheck passed. 34 of the 35 were stale rather than wrong — true earlier, then invalidated by an edit. Judged by: four model subagents labelling blind to a rubric; the author notes 29 of 104 were only medium confidence, and that the per‑agent split is not a model ranking.

figure 03 24 of 265

“done, tests pass” reports that did not hold on re-run

The nomArmy project, rayson‑tech/nomarmy, docs/findings.md. One machine, 16 days to 4 October 2026, 547 jobs across local models, Codex, Claude and Grok. About 1 in 11.

Counted: a job whose worker reported STATUS: done with TESTS: pass. Judged by: the harness re‑running the verification profile in a fresh sandbox. 16 failed outright; the other 8 passed but still passed with the change reverted, so the tests proved nothing. 5 more were not_run. The authors say plainly it is not a benchmark.

figure 04 19 of 45

tasks declared successful while hidden tests failed

“Cowrie”, “Why AI coding agents say all tests pass”, 25 June 2026. One afternoon, 45 failing Python suites, GLM‑5.2 and Claude Opus. 42%.

Counted: a task. All 45 passed the tests the agent could see; 26 passed the ones it could not. Judged by: a hidden suite. Both models failed the same 19 tasks, which makes this as much a measurement of the visible/hidden split in the task set as of either agent.

figure 05 0.0–6.8%

false “done” claims, across three models

Kirilland, “I measured ‘done’ claims 90 times”, 12 August 2026. 30 tasks × 3 rounds per model: 0.0% frontier Claude, 2.4% Codex, 6.8% Haiku 4.5.

Counted: a claim extracted from the final message — 89, 85 and 73 of them respectively, so the three percentages do not share a denominator. Judged by: a deterministic check.sh, independent of the extractor. The author’s own finding is the sharpest one here: Codex read 0.0% in round one and 2.4% over three, Haiku 12.5% then 6.8%. A single measurement lies.

this index —

not yet computable, and published as such

The definition is in /02 and the code is public. What is missing is sessions: nobody outside I‑Ops has contributed one, because there is nothing built to contribute with yet.

Publishing a figure from our own machines, or from ten friendly ones, would produce a sixth incomparable number and a press release. The gate is in /05, and it is the one piece of this page that costs us something.

Why these cannot be averaged, added, or ranked

They differ on four axes at once, and a difference on any one of them is enough to make two figures incomparable:

  • The unit. A trajectory, a message, a job, a task, a claim. A per‑message rate and a per‑job rate cannot be the same number even for identical behaviour, because one agent turn can hold several claims and one job can hold several turns.
  • The denominator. One filters to runs that made an explicit status claim; one counts every claim‑bearing message; one counts jobs whose worker reported done; one counts tasks attempted. Filtering to the runs that spoke raises the rate mechanically, whatever the agents did.
  • What false means. Contradicted by environment state; untrue at the moment written, so a claim that was true an hour ago counts; failed on re‑run or passed while proving nothing; hidden tests failing; contradicted by a script. One of these counts a stale truth as a lie and another does not, and that choice alone moves a figure by tens of points.
  • Who judged it. An environment, four model labellers, a sandbox re‑run, a hidden suite, a shell script. Two of the five are model‑judged, and the one paper that measured model judges on this task found them close to a coin flip.

Three of the five say so themselves: one developer over two weeks, one machine over sixteen days, one afternoon. None of them is doing anything wrong. They are honest one‑off measurements, and the absence they share is the absence of a fixed definition anybody could apply to their own sessions and get a number that lines up with anybody else’s.

/04   contributing a session

What would leave your machine, written down before anything is built to send it.

not built yet

As of 30 October 2026 there is no contribution command, and nothing in the published packages sends anything anywhere. assurance reads the transcripts your agent already keeps, computes locally, and prints. This section is the design it will be built to, published first so it can be argued with first.

/01

Off by default, and per session.

Not an install‑time setting, not an account preference, and not a switch that stays on. Contribution is a decision you make about one session, each time, and the default when you say nothing is that nothing is sent.

/02

The exact payload is printed before it is sent.

Every byte, on your terminal, as it would be transmitted — then a prompt. Not a description of the payload and not a schema in the documentation: the thing itself. If it is too long to read, it is too long to send.

/03

Derived counts only.

Whether the last message made a claim; which of the four states in /02 the record showed; how many edits and how many recognised test runs the session held; which agent and model the transcript names; the version of the tool and of the method; the date. A contribution id generated at random on your machine, so distinct machines can be counted — it identifies an install, never a person.

/04

What is never in it.

No file names or paths, no repository or folder name, no commands, no test output, no prompts, no agent replies, no session identifier from your machine, no diff, and no fragment of the claim itself. Not redacted or hashed — absent, because the computation that produces the counts has already finished and the number does not need them.

/05

Local is the default, and the claim says so.

This page says by default rather than never, and it will keep saying it. Where data may go is configurable; the sentence describing it must not be. A claim that is true for most users and said to all of them is the defect, and it is one we would rather write down in advance than be caught by.

You can check the first half of that today rather than taking it on trust: the packages are Apache‑2.0 and there is no network client in them to find. What the website itself collects is on its own page.

/05   the gate

The number publishes at 25 sessions from 10 machines. Not before.

0 of 25 · 0 of 10

A recurring index needs a sample before it is an index rather than an anecdote with a schedule. This is the threshold, set in advance so it cannot be moved once a number looks appealing.

  • required25 contributed sessions
  • requiredfrom 10 distinct machines outside I‑Ops
  • today0 sessions, 0 machines
  • why zerono contribution path exists yet
  • until thenthe method is published, the number is not

The zero is worth being precise about. It does not mean people were asked and declined. It means /04 is a design and not yet a command, so there has been nothing to decline. When that changes, this page will say how many and from how many machines, on every visit, whether or not the number flatters us.

Why publish the method before the number, when the number is the thing people would link to? Because the alternative is the one thing we have no standing to do. This company exists to argue that a worker does not get to certify its own output, and that a figure with no reproducible method behind it is not evidence. A sixth incomparable percentage, published by the company selling the fix, would be exactly the artefact we tell people not to trust — and it would be worth less than this page, because anybody can produce a number and nobody else has published a definition you could argue with.

So the method is the asset. Disagree with the definition in /02 and the useful move is to say which line is wrong, because it is specific enough to be wrong. That is the property the five figures above cannot offer, and it is the only one that survives an adversarial reader.
